## 1. Executive Summary

Pelipäivä is a feature-rich, local-first PWA with an unusually disciplined test culture for its size
(392 substantive vitest cases, zero skipped tests, a self-tested harness). However, the council
identified **five crash/integrity paths with no safety net**, a **family-cloud API whose destructive
and parse paths can fail open**, and **two god-modules** (`src/lib/stats/statsEngine.ts` at 1735
lines, `src/App.tsx` at 942 lines) that concentrate risk and block refactoring.

The single highest-leverage structural investment is decomposing those two modules; the single most
urgent correctness fix is the invalid `"HH:24"` end-time crash in the freeform parser.

Top 5 by weighted council vote:

| Rank | Finding | Votes |
|---|---|---|
| 1 | F-13 God-modules + synthetic real-child data shipped in prod bundle | 7 |
| 2 | F-04 No error boundary / global rejection trap anywhere | 6 |
| 2 | F-16 Fetches without timeout; unbounded caches | 6 |
| 2 | F-20 Flaky-by-design tests (wall clock, timing thresholds, setTimeout IDB mock) | 6 |
| 2 | F-21 Dead/duplicated code clusters | 6 |

## 2. Methodology

This audit was produced by a **20-agent cross-examination council** running in four phases:

1. **Phase 1 — Archetypes**: 20 reviewer personas, each with a fixed lens (defensive programming,
   zero-defect delivery, scalability, security, a11y/i18n, algorithmic correctness, resource
   efficiency, etc.).
2. **Phase 2 — Independent audits**: five parallel deep-exploration passes covered (a) core app +
   storage + configs, (b) `lib/agents` + `lib/ai` + `lib/api`, (c) data/weather/sync/stats/calendar/
   reconciliation, (d) the entire test tree, (e) docs/worker/scripts/CI.
3. **Phase 3 — Fact-checking**: contested claims were re-verified by direct file reads before being
   admitted into the vote. Three claims were *adjusted*, one was mostly *debunked* — see §5.
4. **Voting**: each of the 20 agents cast exactly 5 weighted votes → 100 votes total across
   25 distinct findings.

**Evidence standard**: no finding is listed without an exact file path and line reference that can be
re-checked today (see §8 for verification commands).

## 3. What Is Genuinely Good

A fair audit must state strengths, because they constrain how fixes should be designed:

- **Strict TypeScript actually enabled**: `strict` and `noUncheckedIndexedAccess` are ON
  (`tsconfig.app.json:19,23`) — rare and valuable; violations are localized escapes, not defaults.
- **Real tests, not vanity**: zero `expect(true)`, zero `.skip/.only`; strong examples include
  `tests/e2e/tier1_features/f06_dexie_schema_v2.test.ts:27-118` (round-trips through real db
  functions) and `t0_family_share_backup.test.ts:130-155` (field-level backup round-trip).
- **The harness tests itself**: `tests/helpers/harness.test.ts:26-255` covers CRUD, all fixtures,
  and the fetch mock manager.
- **Best-in-repo network code**: `torneopalGet` (`src/lib/api/torneopalClient.ts:132-206`) has
  timeouts (`AbortSignal.timeout(10000)` at :187), body-level rejection checks, guarded JSON parse,
  and attempt de-duplication. This is the pattern every other fetch site should copy.
- **Edge Worker is thoughtfully hardened**: hostname allowlist proxy blocking IP-literals,
  credentials, non-443 ports (`cloudflare-worker/worker.ts:79-95,109-121`); schema-validated PUT
  with field truncation (:230-240); rate limiting (:40-69); secrets kept out of the repo
  (`wrangler.jsonc:6-7`, `.gitignore:48-52`).
- **Accurate ops documentation where it matters**: `docs/FAMILY_CODES_OPS.md` matches the Worker
  implementation error-for-error (403 ↔ `worker.ts:161`, TTL ↔ `worker.ts:257`, rate table ↔
  `worker.ts:40-41`).
- **CI exists and is lean**: typecheck → vitest → build on every push (`.github/workflows/ci.yml:27-37`),
  plus automated Pages + Worker deploy (`cd.yml`).
- **Excellent fixture library**: 12 realistic ICS/HTML/JSON feeds under `tests/fixtures/`.

### F-01 · Invalid `"HH:24"` end time crashes event conversion *(severity: Critical)*

**Votes:** 5 · **Area:** AI message parsing → event ingestion

**Root cause**
In `src/lib/ai/messageParserNLP.ts:146-148`, when no explicit end time is present, the hour is
derived as `const endH = (h + 1).toString().padStart(2, '0')` with **no modulo wraparound**. A
kickoff of `23:xx` therefore produces `endTime = "24:xx"`.
Downstream, `src/lib/ai/localAiEngine.ts:50-52` builds dates via
`new Date(\`${dateStr}T${endTime}:00${offset}\`).toISOString()` → JavaScript throws
`RangeError: Invalid time value` for hour 24. Note the sibling warmup derivation
(`messageParserNLP.ts:154-155`) *does* wrap correctly (`totalMins < 0 → += 1440`), proving the
omission is accidental, not intentional.

**Proof**

```ts
// src/lib/ai/messageParserNLP.ts:143-148
if (!end) {
  const [hStr = '15', mStr = '00'] = kickoff.split(':');
  const h = Number(hStr);
  const m = Number(mStr);
  const endH = (h + 1).toString().padStart(2, '0');   // ← 23 + 1 = "24"
  end = `${endH}:${m.toString().padStart(2, '0')}`;
}
```

```ts
// src/lib/ai/localAiEngine.ts:50-52
const startTime = new Date(`${extracted.dateStr}T${extracted.kickoffTime}:00${offset}`).toISOString();
const endTime   = new Date(`${extracted.dateStr}T${extracted.endTime}:00${offset}`).toISOString(); // ← throws
```

**Impact**
Any WhatsApp/message import containing a late evening kickoff ("alkaa klo 23:05") without an explicit
end time crashes the import flow with an unhandled RangeError.

**Fix**
1. Wrap the hour: `const rolled = h + 1 >= 24; const endH = String((h + 1) % 24).padStart(2, '0')`
   and carry the day-roll so the consumer can advance `dateStr` by one day (prefer storing a
   **duration in minutes** instead of a wall-clock end).
2. Add regression tests: kickoff `23:00`, `23:59`, `00:15` next-day semantics, and warmup parity vs
   `messageParserNLP.ts:154-155`.
3. Defensive backstop: validate `HH < 24` in `convertExtractedToMatchdayEvent`
   (`localAiEngine.ts:35-60`) and throw a typed `ParseError` with the offending text instead of a raw
   RangeError.

### F-02 · Unguarded venue coordinate dereference on navigation *(severity: High)*

**Votes:** 2 · **Area:** UI navigation

**Root cause**
The type system says coordinates always exist: `VenueInfo.coordinates: Coordinates` is required
(`src/types/matchday.ts:39`). But source data does not guarantee it:
`OfficialLeagueFixture.venueLat?/venueLng?` are optional (`src/types/matchday.ts:244-245`). Two call
sites dereference directly:

**Proof**

```ts
// src/App.tsx:754-757  (MissionControlHUD navigate)
window.open(
  `https://www.google.com/maps/dir/?api=1&destination=${ev.venue.coordinates.lat},${ev.venue.coordinates.lng}`, ...
// src/App.tsx:831-834  (TimelineCalendarView navigate) — identical pattern
```

**Impact**
Clicking "Navigate" on any event built from a fixture lacking coordinates throws `TypeError: Cannot
read properties of undefined` inside a click handler — user-visible dead button or crashed handler.

**Fix**
1. Add a builder/invariant helper (e.g., `ensureVenueInfo()` in `src/lib/clubs/attachTeam.ts`) that
   materializes `coordinates` (or a documented `null` marker) once at ingest.
2. At both call sites fall back to a text-destination Maps URL using `ev.venue.name`, or disable the
   button when coordinates are absent.
3. Consider making `coordinates` explicitly optional in the type so the compiler enforces handling.

### F-03 · Weak family-code entropy + unauthenticated reads expose child data *(severity: High)*

**Votes:** 3 · **Area:** Family cloud sync / privacy

**Root cause**
Family codes are generated with `Math.random()`:

```ts
// src/lib/sync/familyCode.ts:14-16
export function generateFamilyCode(): string {
  const pick = () => CROCKFORD_ALPHABET[Math.floor(Math.random() * CROCKFORD_ALPHABET.length)];
```

5+1 Crockford-32 chars ≈ 2³⁵ ≈ 31M keyspace. The Worker authorizes purely by code knowledge: GET has
no auth header (`src/lib/sync/familyCloud.ts:44-48`) and responses are sent with wildcard CORS
(`cloudflare-worker/worker.ts:128`). Payloads contain children's first names and team URLs in
plaintext JSON (`familyCloud.ts:343-353`).

**Mitigating facts (verified)**: rate limiting caps GET at 20/900 s per IP-PoP (`worker.ts:40-41`),
which materially raises enumeration cost; unknown codes fail closed with 403 (`worker.ts:160-165`);
codes are never committed to the repo.

**Impact**
Residual risk rated **High**: a determined attacker with IP rotation can enumerate codes and read
children's names/schedules. GDPR-sensitive data behind a 31M keyspace.

**Fix**
1. Switch generation to `crypto.getRandomValues()` (available in browsers and Workers).
2. Narrow CORS from `Access-Control-Allow-Origin: *` to the production origin(s)
   (`https://pelipaiva.pages.dev`).
3. Optional hardening: derive a per-code HMAC secret at issuance and require it as a header;
   lengthen codes to 7+1 chars.
4. Consider encrypting roster payloads client-side keyed from the code so KV contents are opaque.

### F-04 · No global failure net: no ErrorBoundary, unhandled rejections, unsafe JSON.parse *(severity: Critical)*

**Votes:** 6 · **Area:** App shell / resilience

**Root cause**
Nothing catches top-level failures. Verified absences (repo-wide grep): no `ErrorBoundary`,
no `getDerivedStateFromError`, no `window.onerror`, no `unhandledrejection` listener anywhere in
`src/`. The app mounts bare:

```ts
// src/main.tsx:6-10
createRoot(document.getElementById('root')!).render(
  <React.StrictMode>
    <App />
  </React.StrictMode>,
);
```

Concrete unguarded async paths:
- `runBackgroundSync()` called bare every 180 s and on visibility/online events (`src/App.tsx:103,110,116`)
- URL-param join/import IIFEs with no `.catch()` (`src/App.tsx:140-147,155-163`)
- `handleClearData` awaits two clears with no try/catch, wired directly as event callbacks (`src/App.tsx:278-283`)
- `JSON.parse(existingStr)` on possibly corrupt localStorage (`src/App.tsx:477`)
- `JSON.parse(localTombstonesStr)` with no try/catch aborts the whole family sync (`src/lib/sync/familyCloud.ts:297`)

**Impact**
Any rejected promise or corrupt stored value surfaces as a silent failure or full blank-screen crash
with zero recovery UI — fatal for an offline-first PWA used in car parks.

**Fix**
1. Add a class ErrorBoundary around `<App/>` in `main.tsx` with a Finnish recovery screen
   ("Jotain meni rikki — päivitä tai tyhjennä tiedot").
2. Register `unhandledrejection`/`error` listeners in `main.tsx` that log with a `[PELIPAIVA:*]` tag.
3. Wrap the four async paths above with try/catch + user-visible toast.
4. Introduce `safeJsonParse<T>(raw: string | null, fallback: T): T` in a small util; replace both
   unguarded parses.

### F-05 · "E2E" suites are Node tests; adversarial guards are vacuous; browser tests not in CI *(severity: High)*

**Votes:** 5 · **Area:** Test suite honesty & CI gating

**Root cause**
Every tier0–tier5 file imports from `'vitest'` and runs in Node (`vitest.config.ts:6-8`: environment
`'node'`, includes `tests/**/*.test.ts`). Only two specs run under Playwright
(`playwright.config.ts:4` → `testDir: './tests/e2e/playwright'`). Meanwhile CI never launches a
browser (`.github/workflows/ci.yml:27-37` runs tsc + vitest + build only).

Worse, three adversarial security suites wrap **all** assertions in `if (result) {...}`:

```ts
// tests/e2e/tier5_adversarial/m1_adversarial_parser_extractor.test.ts:52-61 (also :93-101, :115-122)
const result = parseAssociationUrl(url);
if (result) {          // ← if the parser rejected EVERYTHING, the test still passes
  expect(result.sport)...
}
```

**Impact**
False confidence: XSS/SQLi/spoof resistance is unproven (the parser could pass by rejecting all
input including legitimate URLs), and real browser regressions ship undetected.

**Fix**
1. Rename `tests/e2e/tierX` → `tests/integration/tierX` (honest taxonomy).
2. Rewrite vacuous guards: assert legitimate control URLs still parse *and* malicious ones return
   null — both directions, unconditionally.
3. Add a Playwright job to `ci.yml` (headless Chromium is already installed as a devDependency).

### F-07 · Lightning-safety logic has truthiness bugs at the edges *(severity: High — safety-critical)*

**Votes:** 2 · **Area:** Weather safety engine

**Root cause / proof** — `src/lib/weather/lightningSafety.ts`:
- Line 58: `if (nearestStrikeKm && nearestStrikeKm <= 20)` — a strike at **exactly 0 km** is falsy,
  so the "watch" branch is skipped and status returns `'clear'`. Must be `!== undefined`.
- Line 35: `!mostRecentStrikeWithin10kmTimeMs` treats epoch-0 timestamps as "none".
- Lines 43-44: a future-dated strike yields negative elapsed time which still satisfies `< 30`,
  producing a danger alert with inflated `resumeCountdownMinutes`.
- Lines 26-31: `strikesWithin30kmCount` counts strikes of any age — stale feeds inflate counts while
  status stays clear.

**Impact**
This module recommends suspending children's sports matches. Edge inputs produce the wrong advice.

**Fix**
Use `!== undefined` guards; clamp negative elapsed to 0; add a feed-age parameter (ignore strikes
older than N hours); extend `lightningSafety.test.ts` with 0-km, epoch-0, future-strike, and
29/31-minute boundary cases.

### F-10 · Reconciliation contradicts its own contract *(severity: High)*

**Votes:** 4 · **Area:** Fixture↔calendar matching

**Root cause / proof** — three verified defects:
1. Day matching uses **UTC calendar-day equality** while the comment claims ±24h tolerance
   (`src/lib/reconciliation/reconciliationEngine.ts:76-85`). Fact-check note: impact direction is
   early-morning local events (00:00–02:59 EET / 00:00–02:59 EEST map to previous UTC day) — e.g.,
   overnight tournaments and mis-zoned feeds. Evening events are unaffected.
2. Learned aliases grant similarity **1.0 on substring containment**
   (`reconciliationEngine.ts:100-105`): alias "honka" blesses "FC Honka Musta" ↔ "Honka II".
3. Missing-component generosity adds +0.1 twice when age-group/squad info merely absent
   (`teamNameMatcher.ts:283-285,299-300`): bare "HJK" vs "HJK T13 Sininen" scores 0.8 on unproven
   squad equality.

**Impact**
Wrong auto-matches merge the wrong fixture onto a child's calendar (threshold ≥0.85 at
`reconciliationEngine.ts:139-141`); correct early-morning matches are never found.

**Fix**
1. Build day keys in Europe/Helsinki (reuse `getFinnishTimezoneOffset`, `statsEngine.ts:481-497`) or
   compare absolute instants within a true ±24h window as the comment promises.
2. Require alias equality of the canonical club token, not substring containment.
3. Drop the double generosity bonus; make absence neutral rather than positive evidence.

### F-11 · ICS ingestion cluster: device-TZ bug, no recurrence, unstable ids *(severity: High)*

**Votes:** 5 · **Area:** Calendar ingestion

**Root cause / proof** — `src/lib/calendar/icsParser.ts`:
1. `resolveEventTimes` uses runtime-local `setHours()` (`:249-250,:267-268`) to apply description
   times like "klo 15:00" — on devices outside Helsinki these land on the wrong instant/day.
2. Zero RRULE/RDATE/EXDATE support (`:489-493` iterates VEVENTs only): recurring trainings appear
   once, ever.
3. All-day DATE values flow through kickoff-time fabrication (`:226-231`).
4. Event id fallback `event-${Date.now()}-${random}` (`:545`) breaks dedupe — duplicates accumulate
   across re-syncs.
5. Venue geocoding awaited serially per event (`:491,:538-542`) — O(n) sequential network on sync.

**Impact**
Wrong times for international users, missing recurring events, duplicate cards after every sync, and
slow ingestion of large feeds.

**Fix**
Derive wall times with an explicit `Europe/Helsinki` formatter (same technique as
`helsinkiDateISO` in `src/lib/agents/time.ts:4-11`); expand recurrence via ical.js'
recurrence iterator; id = stable hash of UID (fallback UID-only); batch geocode with capped
concurrency (≈4).

### F-12 · DST week ranges end one hour early; planner hardcodes `+03:00` *(severity: Medium)*

**Votes:** 3 · **Area:** Time-window math

**Root cause / proof**
`helsinkiWall` probes DST at 12:00 UTC of the target date and stamps the whole day with that offset
(`src/lib/agents/time.ts:21-25`); `sportsWeekRange`/`sportsWeekendRange` then compute Sunday-end
instants (`time.ts:60`,`:98`) that land 1 h early on October fall-back Sunday (23:59 local is +02:00,
probe said +03:00). Separately, `planner.ts:42,:103` hardcode literal `+03:00` instead of computing
the offset.

**Impact**
Events between 22:00–23:59 on the October transition Sunday fall outside "this weekend"; planner
abstraction breaks near midnight boundaries.

**Fix**
Compute per-instant offsets via `Intl.DateTimeFormat('fi-FI', { timeZone: 'Europe/Helsinki',
hourCycle: 'h23' })`; share one implementation between `time.ts` and `planner.ts` (see also F-21
duplication).

### F-16 · Fetches without timeout; unbounded client caches *(severity: High)*

**Votes:** 6 · **Area:** Network robustness / memory

**Root cause / proof**
- No AbortSignal/timeout: family GET/PUT (`sync/familyCloud.ts:44,:96`), LIPAS + HEL geocoding
  (`geo/sportsGeocoder.ts:335,:376`), ICS ingest (`clubs/ingestOfficial.ts:167`)
- FMI memo cache is an unbounded module-level `Map` that **caches rejected promises forever**
  (`weather/fmiWeatherEngine.ts:50,:58-64`) → memory growth + permanent negative caching per session
- Tombstones grow monotonically forever (`familyCloud.ts:296-307`)

**Contrast**: `torneopalClient.ts:187` already demonstrates the correct pattern
(`AbortSignal.timeout(10000)`).

**Impact**
Hung imports on flaky networks; a single transient FMI outage poisons weather for the rest of the
